# Diagram Selection Guide

## 目的

図は「見栄え」ではなく「情報伝達」を目的とする。

Codexは図を生成する前に、まず伝達したい内容を分析し、最適な図種別を選択すること。

複数の図で表現可能な場合は、読者が最も理解しやすい図を優先する。

## 図選択フロー

### 1. 処理の流れを説明したい

選択:

- Flowchart

例:

- ログイン処理
- バッチ処理
- AI生成フロー
- デプロイ手順

特徴:

- 処理順序が重要
- 条件分岐が存在する

### 2. 時系列のやり取りを説明したい

選択:

- Sequence Diagram

例:

- API通信
- Webアプリ処理
- RAG検索処理
- OAuth認証

特徴:

- 誰が誰に何を要求するか
- 時間軸が重要

### 3. システム全体構成を説明したい

選択:

- Architecture Diagram

例:

- AWS構成
- マイクロサービス構成
- AIシステム構成

特徴:

- サービス間の接続
- インフラ構成

### 4. データの流れを説明したい

選択:

- Data Flow Diagram (DFD)

例:

- RAG
- ETL
- 分析基盤
- データ収集

特徴:

- データがどこから来てどこへ行くか

### 5. 状態変化を説明したい

選択:

- State Diagram

例:

- 注文状態
- ワークフロー状態
- AI実行状態

特徴:

- 状態遷移が主題

### 6. 利用者視点を説明したい

選択:

- Use Case Diagram

例:

- 会員登録
- 管理者機能
- システム利用範囲

特徴:

- ユーザー中心

### 7. データ構造を説明したい

選択:

- ER Diagram

例:

- DB設計
- テーブル関連
- RAGメタデータ管理

特徴:

- エンティティと関連性

### 8. オブジェクト設計を説明したい

選択:

- Class Diagram

例:

- Java
- C#
- TypeScript

特徴:

- クラス構造
- 継承関係

注意:

- 技術書・入門書では過剰利用しない

### 9. 画面の遷移を説明したい

選択:

- Screen Transition Diagram

例:

- Web画面
- モバイルアプリ

特徴:

- ユーザー操作中心

### 10. 概念を整理したい

選択:

- Concept Diagram

例:

- AI開発の考え方
- 責任分界点
- 学習ロードマップ

特徴:

- 技術的な厳密性より理解優先

## 優先順位

技術書・動画・教育資料では以下を優先する。

1. Concept Diagram
2. Flowchart
3. Sequence Diagram
4. Architecture Diagram
5. DFD
6. State Diagram
7. ER Diagram
8. Use Case Diagram
9. Class Diagram

Class Diagramは設計資料以外では原則使用しない。

## Codex Decision Rules

図を作成する前に以下を判断すること。

1. 誰向けか
2. 何を理解させたいか
3. 時系列が重要か
4. データが重要か
5. 状態変化が重要か
6. 構成が重要か

その結果に基づいて図種別を選択すること。

不明な場合は Concept Diagram を選択する。

複数候補がある場合は読者の理解負荷が最も低い図を採用する。
